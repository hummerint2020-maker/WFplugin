No new option, so "off changes nothing" holds trivially. `tests/golden/expected.json` stays empty (only `release` changes, to 3.31.134). No schema change, no upgrade path. ## 2. New classes (`WorkforceOne\People`, `src/People/` and `src/People/Data/`)

- **Ports** (interfaces in `src/People/`), held by `PeoplePorts` (constructor gains them; only `trait-services.php` builds it): `OrgClock` (`now()`, `today()`, `timestamp()` = `current_time('mysql'|'Y-m-d'|'timestamp')`; deriving them from one clock would change `org_moves_recover`'s mix of `strtotime(applied_at)` and `current_time('timestamp')`), `Actor` (`userId()` = `get_current_user_id()`, read at the INSERT for `created_by`; cron gives 0), `OrgApprovals` (`reassignSupervisor(int $e,int $from,int $to,int &$pending)` returns `int|false` → `approval_reassign_supervisor`, via a closure made in plugin context because of the by-reference argument; `tellNewManager(int $e,int $to,int $pending)` → `approval_reassign_notify`), `EmployeeChanged` (`changed(int $e,int $wpUserId)` → `invalidate_employee_runtime_cache`). - **Stores** (SQL copied verbatim from the current code; raw wpdb values: `int|false` for writes, `?string` for `get_var`, `(array)` lists, `is_object($r)?$r:null` rows): `ReportingStore` gains `deactivate`, `deactivateSupervisor`, `insertLine`, `insertId`, `lastError`; new `OrgMoveStore`/`WordPressOrgMoveStore` (`tableExists`, `scheduledIdFor`, `insert`, `insertId`, `updateClaimed`, `dueRows`, `claim`, `markAlreadyDone`, `release`, `fail`, `applyingRows`, `resume`, `failInterrupted` (the `$where` of `org_moves_recover` built verbatim, double prepare kept), `byId`, `cancel`, `doneRows`, `openRows`, `failedRows`); `DepartmentStore` gains `byId`, `adminList`, `duplicateFlags`, `update`, `insert`, `insertId`, `archive`, `activeEmployeeCount`, `activeId`, `activeNames`; `TeamStore` gains `tableExists`, `activeCountInDepartment`, `activeById`, `adminList`, `pageEmployees`, `duplicateFlags`, `update`, `insert`, `insertId`, `deactivateMembersOfTeam`, `memberId`, `reactivateMember`, `insertMember`, `archive`, `deactivateAllMembers`, `activeDepartmentOf`, `managedIn`, `deactivateMembershipsOf`, `isActive`, `lastError`; `PeopleStore` gains `importRows`, `setJobTitle`, `departmentIdOf`.
- **Services** (no SQL, no WordPress; `People` and `Organization` namespaces only): `ReportingService` (`setRelationship` returns `int|array{code,message}`, `setSupervisor`, `relationshipSave` with the two ignored results of quirk c), `OrgMoveService` (`check` reads in the order of the old code and never memoises `OrgTree`/`managerIds`; `supervisorChange`: begin (no rollback when it fails) → `setSupervisor` → `reassignSupervisor` → insert or claimed update → commit → `tellNewManager`; `setSupervisorOnly`, `apply` (forget employee, audit with the steps suffix), `schedule` (insert result ignored, quirk j), `summary`, `applyDue`, private `recover`/`failed`, `cancel`, `forChart(callable $row)`), `OrgImportService` (`people`, `apply`), `DepartmentService` (`save`, `archive`, reads), `TeamService` (`save` returning `{error,rolled_back}`, `archive`, `syncEmployeeTeams`, reads). - Controllers keep capability checks, `check_admin_referer`, input parsing, `ensure_*_schema`, `org_enabled()` and the transients, the redirect helpers with their exact arguments, `wp_die` texts and `exit`.

## 3. Transactions, lock order, claims

1. A move now (chart, import, cron, `employee_update` with the chart on): reads, then BEGIN → relationships (UPDATE then INSERT) → approval_steps (SELECT ids, UPDATE, substitute route, COUNT) → org_moves (claimed UPDATE or INSERT) → COMMIT; after the commit: notify the new manager, `people_user_id` read and cache invalidation, name reads, audit. A failed START returns with no ROLLBACK; any later failure ROLLBACKs and nothing else happens.
2. Supervisor only: BEGIN → relationships → COMMIT.
3. Cron and hourly visit: actor 0 for cron, the visitor for the hourly visit (gated by the transient `ews_org_moves_checked`). Claim protocol with no locks: `scheduled→applying` `===1`; the final claimed UPDATE inside the transaction must be 1; every follow-up (`markAlreadyDone`, `release`, `fail`) carries the claim `$where`; `recover` runs first (wait under 900 s, resume once, otherwise failed/interrupted, each through a conditional UPDATE `===1` before its audit).
4. Schedule: one INSERT and an audit. Cancel: SELECT, a conditional UPDATE (result ignored), the audit.
5. Departments: no transaction. Teams: `team_save` BEGIN → teams → members → COMMIT → audit; validation errors still send the bare ROLLBACK through `team_redirect_error` (quirk g); after a failure inside the transaction the service has rolled back, so the controller calls `team_redirect_error('save',false)`. `team_delete` and `sync_employee_teams`: no transaction.
6. Relationships page: no transaction (quirk c).

## 4. Golden harness
`tests/golden/exit.php` (shared): `GoldenExit`, `wp_redirect` and `wp_die_handler` filters that throw, and `golden_post($o,$method,$post,$nonceAction,$referer)` (sets `$_POST`/`$_REQUEST` with a real nonce, `REQUEST_METHOD`, `HTTP_REFERER`, calls the public method, returns `{exit,to,message}`). `tests/golden/actions_org.php` (keys `org:*`): the recorder of `actions_people.php`, with dates normalised to placeholders (today, +1, +5 days, the seed's past date) and nonces to `N`, plus in-process fault injection (a `query` filter that rewrites a matching write, `START TRANSACTION` or `COMMIT` into a failing SELECT). Scenarios: the `check` cases, `summary`/`for_chart`, `submit_*` (bad nonce, denied, chart off, errors, move now with a request moved and a notification, no manager, scheduled), `set_supervisor`/`set_only`/`change_direct`/claim lost, faults on submit and set_only, `cancel_*`, `due_*` (ok, archived manager, already in place, resolvable and unresolvable loops, an old date, recover rows, apply again, the hourly gate, no table), `import_*`, `rel_*`, `dept_*`, `team_*`, `sync_*`, and `employee_update` with the chart on and off. Rows dumped per table, plus `approval_steps`, notifications, audit and the org options. `run.py` gets a sanity check so the trace cannot prove nothing (the move-now redirect says `moved`, notifications are not empty, the member-insert fault SQL contains `ROLLBACK`). Pages added: org chart with `focus`, with an import notice, with the preview; departments with an error; teams with an error. Seed: an `ews_org_import_<id>` transient for the admin.

## 8. Risks
Concurrency (two visits running `org_moves_apply_due`: the claims make each move done once; the service keeps no per-run state and never memoises `OrgTree`/`managerIds`; check-then-act on `scheduled_exists` as before); permissions stay in the controllers; `tellNewManager` only after COMMIT, with the by-reference `$pending` passed through the adapter closure (else the count would be 0 and nobody told); audit texts and `user_id` as before; `e2e_org_moves.py` fault injection stays green because the SQL text is the same; multisite (org tables follow the switched prefix, employees stay fixed). No upgrade path.

## 9. Quirks preserved (each fixed in its own release)
From the earlier design: a, b, c, d, e, f. Found now: g (`team_redirect_error` sends ROLLBACK with no transaction open), h (`org_move_cancel` audits and says "cancelled" even when its conditional UPDATE changed nothing, and for a done or unknown move), i (moves done on the hourly visit are audited under the visitor), j (`org_move_schedule` ignores its INSERT result: it audits, returns a stale id, the import counts it), k (the import's title UPDATE does not clear the people memo, outside any transaction), l (a failed START sends no ROLLBACK in `org_supervisor_change`/`org_set_supervisor_only` but does in `team_save`), m (`approval_set_relationship` has no transaction: alone, a failed INSERT leaves no supervisor), n (`sync_employee_teams`, departments and `team_delete` have no transaction; sync deactivates every membership before re-adding), o (a due move with an out-of-range date is still applied), p, q, r (`department_save` reads `code` without `wp_unslash`), s (departments/teams need `manage_options`, org pages `ews_manage_employees`).

## 10. Decisions, commit order, test plan
Decided (technical): the three private helpers become private service methods; every function with an outside caller keeps its name and signature; `approval_relationship_save` moves to `trait-employees.php`; port names `OrgClock`, `Actor`, `OrgApprovals`, `EmployeeChanged`.
Open question (product): the order in which the visible quirks h, j, m, n are fixed. **Default until the owner says otherwise: after L4c.**
Commit order (green at each step): 1 the harness on unchanged code (`exit.php`, `actions_org.php`, seed transient, pages, `run.py` check; base == head; a self-test by hand); 2 the `check_layers` namespace list; 3 the ports, `PeoplePorts`, the adapters (unused yet); 4 the Stores, fakes, storage contract; 5 `ReportingService` and the relationship functions; 6 `OrgMoveService` and the `trait-org-moves` delegators; 7 `OrgImportService`; 8 `DepartmentService` and `TeamService`; 9 `modules.json`, baselines, docs, CHANGELOG, version, `expected.json`.
Tests: unit, phpstan, phpcs, `check_modules` (lower), `check_layers`, golden (`org:*`, `actions_approvals`/`actions_people` unchanged), e2e: org_moves, org_chart (+ browser), organization, employees, people, employee_profile, my_profile, approvals, substitutes, self_approval, level_guard, approval_engine, my_approvals, speed, query_batching, schema, people_store, approval_store, request_races, and every `*_mu.php` suite.
